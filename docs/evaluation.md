# 인플루언서 페르소나 채팅·타임라인 RAG 평가 명세

> 상태: **평가 설계 초안**. 질문·정답·사건 추출 표본은 아직 사람이 검수한 gold가 아니며, 검색/모델 평가와 성능 측정도 수행하지 않았다. 이 문서의 수치는 계획 또는 목표이지 결과가 아니다.

## 1. 목적과 실행 경계

최종 평가는 **인플루언서 AI 페르소나와의 멀티턴 채팅 안에서** 과거 활동 근거가 쓰이고 말투/문맥을 유지하면서 모르는 사실을 만들지 않는지 확인하는 것이다. 단일 검색 질의만으로 PoC 완료를 판정하지 않는다. 게시 시각과 사건일, 인물/세션 격리, 출처의 실제 존재와 주장 지지 여부를 각각 평가한다. 사진 보강은 캡션 기준선 대비 이점·새 오류·지연·비용을 확인한 뒤 확대 여부를 결정한다. RAG나 사진 보강의 성능 향상을 전제하지 않는다. [채팅 계약](persona-chat.md).

현재 출발점은 4개 코호트의 정규화 게시물 **1,189건**, 로컬 확보 JPEG **2,413개**다. 정규화 대상 게시물에서 참조하는 고유 JPEG는 **2,384개**이며, 나머지 29개는 출처 연결 검수 전까지 이미지 평가/VLM 입력 풀에서 제외한다. 현재 1,189건의 `event_date`는 모두 `null`이다. 역사적 게시물과 회고 자료이며 원본 영상은 없다. 사진에서 확인할 수 없는 영상 내용이나 최신 활동은 평가 정답으로 만들지 않는다. 공개 문서에서는 실제 계정 대신 코호트 A–D만 사용한다.

- 기존 Python ingestion을 입력 준비에 재사용하고, 독립 TypeScript 코어/NestJS와 격리된 로컬 Supabase에서 평가할 계획이다. 현재 구현 또는 실행 완료를 뜻하지 않는다.
- 먼저 모델 없는 lexical 검색 + 템플릿 답변을 검증한다. 서비스 시작·패키지 설치·모델 호출은 이 명세 작성의 범위 밖이다.
- 모델 선택, 하드웨어/접근 확인, 데이터 이용 조건과 외부 전송 허용 범위, 비용 한도가 확정되기 전에는 유료 호출이나 외부 데이터 전송을 실행하지 않는다. 로컬 모델도 이용 조건과 민감정보 검수를 우회하지 않는다.
- 공개 코드/합성 예제와 비공개 평가 자료의 경계는 [데이터 정책](./data-policy.md)을 따른다. 실제 캡션·사진·이름·계정 매핑·다른 프로젝트 코드·서버 접속 정보는 이 문서에 넣지 않는다.

## 2. 서로 다른 평가 자산

| 자산 | 단위/규모 | 평가 대상 | 예정 비공개 경로 |
|---|---|---|---|
| 사건 추출 검수 표본 | 게시물 50건 | 사건 필드·날짜·불확실성·근거 연결 | `data/evaluation/extraction_posts.jsonl` |
| 검색/답변 평가셋 | 질문 50개 | 검색 recall·근거 답변·미답·비용 | `data/evaluation/questions.jsonl` |
| 페르소나 검수 | 인물4명/revision별 | 정의·말투·설계/미상/출처의 구분 | `data/personas/*.json`, `reports/persona_review/*.json` |
| 멀티턴 채팅 평가 | 4명×3시나리오×5user turns = 12대화/60user turns | 페르소나·문맥·도구→최종답변·미답·UI | `data/evaluation/chat_scenarios.jsonl` |
| 실행 결과/판정 기록 | 실행별 결과 | 조건·원시 출력·사람 판정·실패 사례 | `reports/evaluation/*.json` |

50게시물에서 질문 50개를 자동 생성한 것으로 두 자산을 대체하지 않는다. 같은 게시물이 두 자산에 쓰일 수는 있으나 용도·검수·분할을 별도로 기록하고, 최종 test 근거에 대한 추출 gold를 튜닝에 사용하지 않는다. 한 게시물은 사건이 없거나 여러 사건을 포함할 수 있으므로 게시물 수와 사건 레코드 수도 구분한다.

평가 자산은 초기 `review_status: draft`로 관리한다. 자동 생성 질문/정답과 자동 추출 결과는 후보일 뿐이다. 사람이 원본 캡션/사진과 연결 ID를 검수하고 필요한 수정·근거 범위 확인을 마친 뒤에만 `human_reviewed`로 승격한다. persona 상태 enum은 채팅 계약의 `draft | reviewed | retired`를 따르며 `reviewed`는 검수 기록을 요구한다. 부분 검수는 전체 gold 완료로 보고하지 않는다. 가능하면 작성자와 별도 검수자가 교차 확인하고, 한 사람만 검수한 경우 그 한계를 보고한다.

## 3. 사건 추출 50게시물 검수

초기 배분은 A/B/C/D = **13/12/13/12건**이다. 계정별 무작위 표본만으로 어려운 경우가 빠지지 않도록 명시 날짜·회고·상대 날짜·광고·미래 계획·날짜 불명·다중 이미지·캡션/사진 불일치를 포함하고 선정 방식과 중복 태그를 기록한다. 목적 표집 결과를 전체 1,189건의 모집단 정확도로 일반화하지 않는다.

검수자는 사건 레코드별로 다음을 독립 판정한다.

- 사건 종류/요약/공개 활동 필드가 실제 근거에 있는가. 제3자 이름·관계·민감정보·사생활 추론이 추가되지 않았는가.
- `person_id`, `post_id`, 이미지 참조가 올바른 게시물로 연결되는가.
- 게시 시각, 사건일/기간, 날짜 근거, 시간대, 회고/계획 여부가 구분되는가.
- 이미지 관찰과 캡션 진술이 분리되고, 사진만으로 촬영일·인물 동일성·국적 등을 단정하지 않는가.
- 근거 부족/충돌을 `unknown` 또는 불확실성으로 유지하는가. 검수자의 추측도 정답으로 채택하지 않는다.

보고할 지표:

1. **필드 정밀도** = 근거가 지지하는 예측 필드 수 / 평가 가능한 예측 필드 수. 필드별 분모와 예측 없음 사례를 함께 제시한다.
2. **필수 정보 완전성** = 추출된 필수 gold 필드 수 / 근거로 확정 가능한 필수 gold 필드 수. gold의 unknown은 완전성 분모에서 제외하되 불확실성 보존 평가에는 포함한다.
3. **사건 누락/과잉**: gold 사건과 예측 사건을 근거·활동 단위로 매칭해 누락 및 근거 없는 추가 사건을 센다. 일치 규칙을 평가 전에 고정한다.
4. **날짜/불확실성 정확성**: 사건일 지지 여부, 게시일→사건일 오복사 수, 근거 없는 정밀 날짜 수, gold unknown 보존 비율.
5. **출처 연결 유효율**, **민감/금지 추론 위반 수** 및 실패 사례 유형.

추출 정확도에 대한 임의 합격 수치를 결과처럼 만들지 않는다. 표본 검수 결과·잔여 오류를 먼저 보고하고, 모델 기반 추출 도입 여부는 별도로 판단한다. 이 지표를 검색 질문 50개의 정답률과 합치지 않는다.

## 4. 검색/답변 질문 50개 구성

아래 표는 생성할 질문의 **계획 수량**이며 이미 존재하는 질문이나 검수 완료 건수가 아니다.

| 질문 유형 | A | B | C | D | 합계 |
|---|---:|---:|---:|---:|---:|
| 게시 날짜/기간 및 날짜 기준 확인 | 4 | 4 | 4 | 3 | 15 |
| 주제 조회 | 3 | 2 | 3 | 2 | 10 |
| 기간별 타임라인/요약 | 2 | 3 | 2 | 3 | 10 |
| 시각적 질문 | 1 | 1 | 2 | 1 | 5 |
| 미답/범위 밖 | 3 | 2 | 2 | 3 | 10 |
| **합계** | **13** | **12** | **13** | **12** | **50** |

미답/범위 밖 10개는 계획상 `insufficient_evidence` 6개 + `out_of_scope` 4개로 구성한다. 두 근거 변형에서도 특정 실제 활동을 주장할 근거가 없는 사례로 검수한다. 날짜 기준이나 대상이 모호한 `needs_clarification` 사례는 날짜/기간 유형 등에 포함하고 수량을 별도 기록한다. 답변 가능 질문 수는 40으로 단정하지 않는다. 시각 질문·명확화 질문 때문에 근거 변형별 실제 분모가 달라질 수 있다.

| 유형 | 기대 출력 | 대표 실패 |
|---|---|---|
| 게시 날짜/기간 | 지정 인물·기간의 게시물, `posted_at` 기준임을 표시; 사건일 질의는 확정된 사건 근거만 사용 | 게시일을 활동일로 복사, 시간대 경계 누락, 다른 인물 혼합 |
| 주제 | 근거 있는 주제/활동을 해당 게시물 ID와 연결 | 단어 동시 출현만으로 활동을 단정, 무관한 게시물 인용 |
| 기간 요약 | 보유 자료 범위에서 사건·회고·계획을 구분하고 누락/불확실성을 표시 | 모든 실제 활동의 완전한 목록처럼 답변, 근거 없는 연결 서사 |
| 시각적 질문 | 사진에서 관찰 가능한 것만 답변; 캡션만으로 안 보이면 미답 | 캡션만으로 이미지 세부 묘사, 얼굴/동행인 동일성·촬영일 단정 |
| 미답/범위 밖 | 근거 없음/보유 범위 밖을 구분해 답변 거절 | 자료 없음→실제 활동 없음, 최신/원본 영상 질문에 사실 창작 |

질문은 특정 과거 기간을 명시한다. “오늘”, “최근”, “작년”처럼 실행일마다 gold가 바뀌는 상대적 현재 질문은 사용하지 않는다. 날짜 명확화 시험이 필요하면 기준 시점·시간대가 고정된 합성 사례로 제한한다.

### 캡션과 이미지의 답변 가능성

같은 `question_id`와 질문 텍스트를 `caption_only` 및 `caption_image`에서 평가한다. 각 변형마다 `answerable`, 기대 상태, relevant 게시물/근거 ID, 필수 주장을 따로 검수한다.

- 캡션만으로 가능한 질문은 두 변형의 공통 답변 가능 집합에서 paired 비교한다.
- 이미지가 필요한 질문은 캡션 변형의 정답이 `insufficient_evidence`일 수 있다. 이를 캡션의 사실 오답으로 벌점화하지 않고 **적절한 미답** 여부를 채점한다. 이미지 변형에서는 관찰 가능한 주장과 인용을 채점한다.
- 이미지도 답할 수 없는 질문은 두 변형 모두 미답/범위 밖이어야 한다. 이미지 추가 자체가 사건일·실제 활동 확정 근거는 아니다.
- 전체 50개의 상태 일치율과 변형별 답변 가능 질문의 사실/검색 지표를 모두 보고한다. 분모가 달라진 지표만으로 이미지 효과를 주장하지 않는다.

## 5. 비공개 gold JSONL 계약(제안)

현재 Python `Post`는 `person_id`, `post_id`, `posted_at`, 캡션/매체 참조와 선택적 `event_date`/`event_date_basis`를 가진 입력 스키마다. 아래는 별도 평가 자산의 **제안 스키마**이지 기존 ingestion 구현 필드가 아니다. 실제 구현 시 [근거 스키마](./evidence-schema.md)의 ID/날짜 계약과 일치시킨다. `relevant_post_ids`는 canonical `source_post_id`를 담고 기존 `post_id`와의 매핑을 보존한다. `relevant_evidence_ids`는 평가용 locator ID이며 비공개 근거 목록에서 `evidence_refs`의 `source_post_id`·`modality`·`media_id`·`selector`로 해석 가능해야 한다. 별도 ID가 존재한다는 것만으로 지지 근거로 인정하지 않는다.

| 필드 | 의미 |
|---|---|
| `question_id`, `person_id` | 안정적 질문 ID, 평가 대상의 비공개 고정 ID |
| `task`, `query` | 위 질문 유형, 질문 텍스트 |
| `date_basis`, `range` | 평가 annotation의 `posted_at`/`event_date`/`none`/`unspecified`; 기간 시작·끝·경계 규칙·시간대. 코어 요청으로 변환하는 규칙은 아래와 같다 |
| `corpus_version`, `gold_version` | 입력 snapshot/정규화 버전, 검수 버전 |
| `split`, `leakage_group_ids` | `dev`/`test`, 공유 게시물·동일 사건·이미지/질문 변형 그룹 |
| `variants` | `caption_only`/`caption_image`별 아래의 기대값 |
| `variants.*.answerable` | 해당 근거 변형에서 답변 가능 여부 |
| `variants.*.relevant_post_ids` | 질문을 지지하는 gold 게시물 ID 전체; document recall의 단위 |
| `variants.*.relevant_evidence_ids` | 캡션 구간/사건/사진 관찰 등 주장 검수용 세부 근거 ID |
| `variants.*.required_claims` | 근거 ID에 연결된 원자적 필수 주장; 문체가 아닌 의미 단위로 채점 |
| `variants.*.unknown_expected` | 알 수 없음으로 남겨야 하는 필드/주장과 이유 |
| `variants.*.expected_status` | `answered`/`insufficient_evidence`/`out_of_scope`/`needs_clarification` |
| `review_status`, `review` | `draft`/`human_reviewed`, 검수자·검수 시점·수정/판정 이력 |

`answered`는 근거 있는 답변, `insufficient_evidence`는 범위 안 질문이나 현재 자료로 확인 불가, `out_of_scope`는 최신 활동·원본 영상 등 보유/제품 범위 밖, `needs_clarification`은 유효한 요청에서 해석 조건을 먼저 명확히 해야 하는 상태다. unknown을 빈 문자열이나 확정 날짜로 바꾸지 않는다.

금지된 추론·무권한 인물 접근·잘못된 입력은 이 네 상태나 50개 유효 요청 평가에 넣지 않는다. [근거 스키마](./evidence-schema.md)의 `policy_rejection`/`validation_error`로 검색·모델 호출 전에 거부하는 별도 계약 회귀 테스트로 검증한다. 같은 이름의 잘못된 alias는 `AMBIGUOUS_ALIAS` 검증 오류이지 답변 명확화 상태가 아니다.

평가 adapter는 `posted_at → posted`, `event_date → event`로 코어의 `date_basis`를 변환하고, `range`를 `[start, end)`의 `date_range` 및 명시적 timezone으로 변환한다. `none`은 기간 조건이 없는 주제 질의 annotation이며 게시물 근거 조회인 경우 명시적으로 `posted`와 `date_range` 생략을 선택한다. `unspecified`는 adapter/해석 계층의 명확화 사례로 평가하고 코어에 잘못된 enum을 보내지 않는다. 실제 사건일을 묻는 질문을 `none`/`posted`로 바꾸지 않으며, 사건일 evidence가 없으면 `insufficient_evidence`다. 날짜 basis/timezone이 미해결이면 유효한 코어 요청을 임의로 생성하지 않고 `needs_clarification`을 반환한다.

다음은 실제 캡션·인물과 무관한 **합성 구조 예제**다. 평가 정답이나 실측 데이터가 아니다.

## 6. 시간과 정답 판정

- `posted_at`의 UTC 원본과 사용자 기간의 시간대를 보존한다. 날짜 범위는 시작 포함/끝 제외로 고정하고 시간대 변환 후 경계를 검증한다.
- 현재의 사건일 미확정 레코드는 확정 사건일 검색의 완전한 coverage로 취급하지 않는다. 해결되지 않은 사건일 질의는 `insufficient_evidence` 또는 기준이 모호한 경우 `needs_clarification`로 응답한다. 게시일 필터로 조용히 대체하지 않는다.
- `event_date`는 명시 근거 또는 검수된 해석이 있어야 한다. 게시 시각을 사건일로 대입하지 않는다. 회고·광고·미래 계획을 당시 실제 활동으로 바꾸지 않는다.
- “어제” 등의 상대 날짜는 발화의 기준 시점과 작성자의 시간대가 검증될 때만 사건 날짜 후보를 계산한다. **UTC 게시 시각에서 무조건 24시간을 빼지 않는다.** 기준/시간대가 없거나 모호하면 unknown 또는 범위/불확실성을 유지한다.
- 게시일 질의와 사건일 질의의 gold를 분리한다. 질문이 그 차이에 따라 답이 달라지고 기준이 불명확하면 `needs_clarification`으로 검수한다.
- “기록을 찾지 못했다”는 “그날 활동하지 않았다”의 근거가 아니다. 불완전한 기록·자료 범위 밖 날짜·검색 실패를 실제 활동 부재와 구분한다.

## 7. dev/test 분할과 누수 방지

초기 목표는 25개 dev + 25개 최종 test다. 질문 수가 작으므로 사람이 전량 검수할 수 있는 규모로 유지한다. 위 유형/코호트 분포를 가능한 한 양쪽에 반영하되 **근거 그룹 격리가 정확한 25/25보다 우선**한다.

- 같은 게시물, 동일 사건의 여러 게시물, 모든 이미지/캡션 변형과 질문 paraphrase는 하나의 연결 그룹으로 묶어 dev/test를 넘지 않게 한다. 여러 게시물을 공유하는 기간 요약 질문도 연결 그룹에 포함한다.
- 연결 때문에 25/25가 불가능하면 질문 선정/기간을 재조정하고 사람이 다시 검수한다. 그래도 불가능하면 실제 split 수·유형·코호트별 수와 이유를 공개 가능한 집계로 보고한다. 그룹을 쪼개 숫자만 맞추지 않는다.
- 검색 corpus에 test의 원본 게시물이 존재하는 것은 평가 목적상 필요하다. 그러나 test 질문·gold·사람 판정·오답을 프롬프트 예시나 튜닝 입력으로 사용하지 않는다. 추출 표본에서 얻은 test 그룹의 gold도 튜닝에서 제외한다.
- 검색 설정, 프롬프트, 임계값, 상태 정책은 dev에서만 조정한다. 최종 test 전 corpus/gold/설정 버전을 고정한다. test를 보고 수정했다면 새 버전의 dev로 취급하고 새로운 미사용 test가 없으면 “최종 held-out 검증”이라 부르지 않는다.

## 8. 비교군과 실행 통제

| 단계 | 비교군 | 목적 |
|---|---|---|
| 모델 없음 | lexical 검색 + 결정적 템플릿 답변 | 로컬 필터·근거 연결·미답 동작 기준선; LLM 성능과 구분 |
| 캡션 LLM 비교 | 동일 LLM의 `no_retrieval`, `lexical_caption_rag`, `semantic_caption_rag` | 검색 방식의 효과/실패 비교 |
| 사진 보강 | 동일 질문의 `caption_only` vs `caption_image` | 이미지 관찰 추가의 이점/오류/비용 비교 |

무검색군은 대상 corpus 근거 없이 답하도록 하되 같은 질문·공통 지시·출력 상태 계약을 사용한다. 빈 근거만 다르게 제공하며 답을 gold로 주입하지 않는다. 모델 없는 템플릿군을 동일 LLM 실험의 무검색군처럼 섞지 않는다.

LLM 비교에서는 모델/버전, 공통 프롬프트, temperature, 최대 생성 토큰, 근거 토큰 예산, top-k, 인물·날짜 필터, corpus 버전을 고정한다. 다른 모델/멀티모달 능력이 필수이면 변경점을 명시하고 순수 이미지 효과로 귀속하지 않는다. semantic군의 임베딩 모델·차원·버전·검색 인덱스 설정을 별도로 기록한다. caption/image 세부 근거가 늘어도 동일 게시물은 하나의 document로 deduplicate한다.

실행 메타데이터에는 run ID, 코드 revision, 도구/런타임 버전, 설정 hash, seed(지원 시), 실행 시각, 장치/병렬도, 재실행 횟수와 순서, warm/cold cache 조건을 포함한다. dev에서 반복 횟수와 측정 정책을 미리 고정하고 모든 실행을 보존한다. 유리한 실행만 골라 보고하지 않는다. temperature 0도 완전 재현을 보장한다고 주장하지 않는다.

웹 검색 baseline은 현재 필수 범위에서 제외한다. 후속 도입 시 웹 snapshot 시점·검색 조건·데이터 전송 허가를 별도 정의하며 최신 웹 결과를 역사적 게시물 gold에 자동 편입하지 않는다.

## 9. 지표와 분모

### 검색

질문별 gold 게시물 집합을 `G_q`, 중복 제거한 상위 5개 검색 게시물을 `R_q@5`라고 한다.

- **document recall@5** = `|G_q ∩ R_q@5| / |G_q|`. 세부 evidence/chunk/이미지 ID가 아니라 `relevant_post_ids`가 분모다. 답변 가능한 held-out 질문 중 gold가 검수된 질문의 macro 평균을 주요 지표로 사용하고 질문 수·gold 게시물 총수·선택적으로 micro 값도 함께 보고한다.
- 미답/명확화/범위 밖 질문 또는 `G_q`가 비어 있는 질문은 검색 recall 분모에서 제외하고 상태/안전 지표로 평가한다. 누락 gold를 빈 집합으로 만들어 제외하지 않는다.
- gold는 질문을 지지하는 corpus 내 관련 게시물을 검수한 전체 집합이다. top-5 결과만 보고 gold를 만들거나 유리하게 relevant 집합을 축소하지 않는다.
- 기간 요약처럼 gold 게시물이 5개를 넘으면 recall@5의 상한은 `5/|G_q|`이다. 해당 질문 수와 상한을 보고하고, 전체 macro 상한 때문에 목표가 불가능하면 목표/질문 범위를 **최종 test 전에** 재검토한다. recall 정의를 바꾸거나 실패를 숨기지 않는다.
- **MRR**은 선택적 보조 지표다. 첫 relevant 게시물의 reciprocal rank를 전체 검수된 답변 가능 질문에서 평균하며 검색 실패는 0으로 둔다. cutoff/검색 깊이를 명시한다. 여러 게시물의 완전성을 대체하지 않는다.

### 답변·출처·안전

| 지표 | 판정/분모 |
|---|---|
| 기대 상태 일치율 | 변형별 gold 상태와 실제 네 상태의 일치 수 / 평가 질문 수; 상태별 confusion matrix 병기 |
| 필수 주장 충족률 | 정확히 표현한 원자적 필수 주장 / gold 필수 주장; 답변 가능 질문에서 평가 |
| unsupported claim 비율/건수 | 제공 근거가 지지하지 않는 사실 주장 / 출력 사실 주장; 출력을 원자 주장으로 나누어 사람이 판정 |
| 출처 유효율 | corpus에 존재하고 요청 인물·근거 변형에 맞는 인용 / 모든 인용; 잘못된 ID·다른 인물·잘못된 매체 참조는 실패 |
| citation support precision | 실제로 연결된 주장을 지지하는 인용 연결 / 모든 주장–인용 연결; 존재하는 ID라도 무관하면 실패 |
| 인용 완전성 | 유효하고 주장을 지지하는 인용이 있는 사실 주장 / 인용이 필요한 출력 사실 주장 |
| missed abstention | gold가 답변 불가인데 확정 답변/근거 없는 구체 활동을 낸 질문 수; 상태만 미답이고 본문은 창작한 경우도 실패 |
| false abstention | 답변 가능한데 미답한 질문 수 / 실제 답변 가능 질문 수 |
| 날짜 혼동 | 게시일/사건일 혼용·근거 없는 정밀 사건일·잘못된 시간대 경계의 발생 질문/주장 수 |
| 인물 혼합/금지 추론 | 다른 인물의 사실 사용, 제3자 식별·민감/사생활 추론 건수 |

출처의 **존재는 주장 지지를 뜻하지 않는다**. 인용이 없는 출력의 출처 유효율이나 사실 주장이 없는 출력의 unsupported 비율은 `N/A`로 보고하고 별도 완전성/상태 지표를 적용한다. 빈 출력을 100% 정확 답변으로 채점하지 않는다. 표현만 다른 의미상 일치와 부분 정답의 규칙을 dev에서 고정한다. LLM judge는 후보 오류 탐지/보조 분석에만 사용하며 사람 검수와 최종 판정을 대체하지 않는다.

### 지연·비용

검색, 임베딩/이미지 전처리, 답변 생성, end-to-end 시간을 구분한다. warm/cold cache별 측정 질문 수, p50/p95와 실행 분산을 보고한다. 이미지 분석/인덱싱 같은 일회성 비용을 질문당 온라인 비용과 분리하고, 호출 수·입출력 토큰·이미지 수·측정 당시 가격/통화 또는 로컬 자원 시간을 기록한다. 로컬 실행을 비용 0으로 표현하지 않는다. 미실행 비용은 추정 여부를 명시하고 실제 측정값과 섞지 않는다.

## 10. 초기 목표와 보고/중단 기준

아래는 제안 목표이며 달성 증거가 아니다.

- 실제 답변 가능한 **held-out** 질문의 document recall@5 **≥90%**. 근거 변형별 실제 질문 수와 gold 분모를 함께 보고한다.
- 출력 인용의 출처 유효율 **100%**, 인물 혼합 **0건**. 별도로 주장 지지 정밀도/인용 완전성을 보고한다.
- unsupported claim **0건**, missed abstention **0건**을 안전 목표로 삼는다. 특히 전체 50문항 안의 미답/범위 밖 **10문항에서 근거 없는 구체 활동 주장 0건**, 게시일/사건일 혼동 **0건**을 확인한다.
- 10문항은 별도 10개짜리 test가 아니라 전체 50개에 포함된다. 최종 test에 들어간 해당 문항이 예컨대 5개라면 held-out 결과의 분모는 실제 5개다. dev+test 10개 점검 결과와 held-out 결과를 분리하며 “10개 모두 held-out 통과”로 바꾸지 않는다.

모든 결과에는 `planned / draft / human_reviewed / executed` 상태, 실제 수량/분모, 제외 사유, 코호트·유형·근거 변형별 결과와 실패 사례를 남긴다. 표본이 작고 같은 코호트/사건에 상관이 있으므로 작은 차이를 통계적 우월성으로 주장하지 않는다. 50문항 성능을 다른 인물·최신 자료·서비스 전체의 성능으로 일반화하지 않는다.

검색 누락, 무근거 주장, 날짜 혼동이 나오면 dev에서 검색·근거/미답 정책을 먼저 수정하고 버전별 실패도 보존한다. 사진 효과가 없거나 새 안전 오류/비용이 커지면 전체 JPEG 분석 확대를 보류한다. 검수 미완료·데이터 사용 조건 미확정·실행 환경 미확정이면 해당 단계는 미수행으로 남기되 모델 없는 로컬 기준선 검증은 별도로 진행할 수 있다.

## 11. 산출물 보관과 다음 검증

`data/evaluation/*.jsonl`과 `reports/evaluation/*.json`은 기존 `data/`, `reports/`, `*.jsonl` ignore 규칙 아래 비공개로 유지한다. ignore는 접근 통제/공개 허가가 아니므로 staged 파일·기존 추적 여부·실행 로그를 별도 확인한다. 실제 질문·정답·실패 출력은 공개 fixture/CI 로그에 복사하지 않는다. 공개 가능 산출물은 합성 예제와 식별 정보를 제거한 방법론/집계뿐이다.

다음 구현에서 필요한 검증은 JSONL 계약/참조 ID 검증, 그룹 분할 누수 검사, 인물·날짜·시간대 경계 합성 테스트, 상태/미답 테스트, recall 분모와 인용 지지 판정의 단위 테스트다. 현재 문서 작성 검증은 계획 합계·상태 계약·날짜/공개 경계 확인이며, 이를 서비스 테스트 또는 RAG 성능 측정으로 보고하지 않는다.

## 12. 페르소나 채팅 PoC — 필수 추가 평가

### 페르소나 검수와 gold 누수

4명 각각 identity/concept/behavior/speech/examples/greeting/boundaries의 revision과 hash를 고정한다. 관찰된 표현·연구용 설계·미상을 구분하며, 감정 반응/구어 억양/친밀 관계를 캡션만으로 사실화하지 않는다. persona의 예시/정적 에피소드에 test 질문의 정답을 미리 넣지 않는다. 스타일 자료는 dev 자료로 선정하고, persona 자체가 근거로 쓰이는 정적 공개 사실은 별도 `profile_refs`로 추적한다. persona에 이미 포함된 사실 질문은 별도 태그/분모로 보고하며 이를 RAG가 새로 제공한 지식으로 세지 않는다.

### 12개 대화 시나리오

각 코호트에 아래3가지, 시나리오마다5user turns를 작성한다. 총60user turns는50개 단일 질문과 **별도**다. 각 시나리오 전체와 공유 source/event/persona 예시는 연결 그룹으로 관리해 dev/test 누수를 막는다. 최종 held-out 대화 수는 실제 그룹 분할 후 보고하며12개 전부를 test라고 부르지 않는다.

| 시나리오 | 턴 구성/기대 검증 |
|---|---|
| S1 일반 대화→과거 기억 | 인사·분야 대화→명시 게시기간→주제 후속→사건일 확인→보유 범위 밖. 말투 유지·retrieval 사용·게시일/사건일 구분·미답 |
| S2 후속 reference·정정 | 같은 인물의 과거 주제→“그때/그것”→모호한 날짜 기준→사용자의 명확화→새 주제. reference 유지, 정확히 필요한 명확화, 이전 모델 발화를 원본 사실로 승격하지 않음 |
| S3 근거 부족·회상 유도 | 일반 대화→근거 없는 활동 질문→“기억나잖아” 압박→실제 확보 범위의 게시물로 전환→이전 답변 요약. persona가 사실을 창작하지 않고 자연스럽게 범위/근거로 돌아옴 |

owner 위반, 다른 인물 tool 요청, prompt injection, 동시 요청/취소/재시도/stream 단절은 별도 합성 계약 회귀다. invalid 요청을 위12개 유효 대화 또는50질문 정답률 분모에 섞지 않는다. 이미지 질문은 caption-only와 image 모드의 answerability를 나누며 필수 텍스트 채팅을 이미지 성능에 종속시키지 않는다.

### 비교 통제

- 필수 모델 비교는 **같은 reviewed persona revision + 같은 모델/settings**의 persona-only(no retrieval), persona+lexical RAG, persona+semantic RAG다. 같은 데이터/policy/정적profile 조건을 유지하며 persona 없는 일반 챗봇을 RAG off로 비교하지 않는다.
- **고정 history 비교:** 사람이 검수한 같은 prefix/history와 같은 target user message를 각 변형에 제공해 다음 턴의 factual/말투/미답 차이를 측정한다. history의 활동 문장은 evidence로 자동 채택하지 않는다. 원본 근거가 없으면 미답이 정답이다.
- **실제 end-to-end 대화 비교:** 같은 user script/초기조건으로 각 변형이 자신의 assistant history를 누적한다. history가 갈라짐을 보고하고 “각 턴의 prompt가 동일했다”고 주장하지 않는다. 명확화 분기는 사전 검수된 branch 규칙으로 실행하며 실제 user turn 수/경로를 남긴다. fixed-history 지표와 합치지 않는다.
- tool request/trace/source snapshot ID/최종 assistant claim 연결을 기록한다. 도구를 실행했거나 근거 카드를 표시했다는 사실만으로 효과를 판정하지 않고 **최종 대화 발화의 내용상 지원**을 사람 검수한다.
- 미래 roleplay/as_of 모드는 미지원이다. 과거 게시물 기반 회상과 “그 시점까지만 알고 있는 인물” 재현을 동일하게 평가하지 않는다.

### 대화 판정과 최소 완료 게이트

| 축 | 판정 |
|---|---|
| 실제 동작 |4명 각각 reviewed persona로 일반 대화와5user turns 이상, 저장/reload, 근거 카드 확인. fake provider UI E2E와 실제 모델 smoke를 구분 |
| 사실/시간/근거 | 사실 원자 claim precision, 출처 존재·지지, 게시일/사건일, 미답/명확화는 기존 정의를 최종 assistant 발화에 적용. 부분/중단 턴은 완료 성능으로 세지 않음 |
| 페르소나 | 정의한 언어·문장 스타일·반응·분야·boundary 유지; 사람이1~5 rubric(1=잦은 위반,3=부분 일관,5=검수 정의와 일관)으로 턴/대화별 판정. 실제 본인과의 심리적 동일성 점수가 아님 |
| 대화 문맥 | 후속 referent/기간 유지 성공·실패, 명확화 필요시 질문, 세션/인물 전환 회귀. 사용자 주장→현실 이력 승격은 위반 |
| 시스템 | tool timeout/error를 미답으로 위장하지 않음, duplicate/cancel/late result/stream 단절·재접속 회귀, 미검증 factual token 미공개 |
| 비용/지연 | turn별 retrieval·generation·validation·최종표시 시간, tool 호출 수·token·비용. 초기status와 최종 content를 나누고 검증 후stream을 provider 실시간이라고 보고하지 않음 |

PoC는4명 정의/검수·최소채팅UI/API·실제 모델 멀티턴·단일질문 및 대화 비교 결과가 있어야 완료다. 표현 후 무근거 활동 추가/게시일 혼동/인물·세션 누출/AI 본인 사칭0건을 목표로 삼고 위반이 남으면 해당 기준 미충족으로 기록한다. 말투 점수의 임의 합격 threshold는 결과를 본 뒤 만들지 않으며, 초기에는 분포/실패를 보고하고 사전에 검수한 필수 언어·boundary 위반은 회귀에서 거부한다. RAG가 더 좋지 않더라도 정확한 부정적 결론과 실패 원인을 보고하되 효과 달성으로 부르지 않는다.

채팅 자료와 run별 transcript/tool trace는 `data/`와 `reports/` 아래 비공개다. 공개 CI에는 합성 persona·합성 대화만 사용한다.
